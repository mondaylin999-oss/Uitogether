# Deploying UITogether to Render

Everything runs on Render — there is no second vendor to sign up for.

| Piece    | Render resource | Source        |
| -------- | --------------- | ------------- |
| Frontend | Static Site     | `frontend/`   |
| Backend  | Web Service     | `backend/`    |
| Database | PostgreSQL      | `database/`   |

> **Note on the database.** This project originally ran on MySQL and was
> ported to PostgreSQL so the database could live on Render alongside the rest
> of the app — Render's managed databases are PostgreSQL only. See
> [What the port changed](#what-the-port-changed) at the bottom if you are
> comparing against the old MySQL schema.

---

## 1. Create the three resources

The repository contains [`render.yaml`](render.yaml), so Render creates all
three in one step.

1. Go to <https://dashboard.render.com> → **New** → **Blueprint**.
2. Connect GitHub and pick this repository.
3. Render reads `render.yaml` and shows `uitogether-db`, `uitogether-api` and
   `uitogether-web`. It prompts for the one value marked `sync: false`:

   | Service          | Variable       | Value                                       |
   | ---------------- | -------------- | ------------------------------------------- |
   | `uitogether-web` | `API_BASE_URL` | `https://uitogether-api.onrender.com/api`   |

   Everything else is wired automatically:
   - `DATABASE_URL` comes from the database via `fromDatabase`.
   - `JWT_SECRET` is generated by Render.
   - `CLIENT_URL` is set to the static site's URL, for CORS.

   Both `API_BASE_URL` and `CLIENT_URL` hard-code an `onrender.com` hostname
   derived from the service names. If you rename a service or add a custom
   domain, update them — `CLIENT_URL` in `render.yaml`, `API_BASE_URL` on the
   static site — or the browser will be blocked by CORS.

   `API_BASE_URL` needs the backend's final URL, which you only know after the
   first deploy. Render derives it from the service name, so the value above is
   almost always right; if the name was taken, copy the real URL from the
   `uitogether-api` page afterwards and redeploy the static site.
   **The `/api` suffix is required.**

4. Click **Apply**.

## 2. The schema loads itself

There is no manual migration step. The API's start command is
`npm run start:migrate`, which applies any pending migration before the server
binds its port. `DATABASE_URL` is already injected into the service and the
database is only reachable from inside Render's private network, so no
credential ever has to leave the platform.

This is safe to repeat: `db:migrate` keeps a `schema_migrations` ledger, so a
redeploy with nothing pending is a no-op, and each migration commits inside its
own transaction — a broken one stops the service from starting rather than
leaving the schema half-applied.

### Optional: demo data

The seed is *not* loaded automatically — it is demo content, and blanket-loading
it into a live database would be wrong. To load it, copy the **External
Connection String** from the `uitogether-db` page (the *internal* one only
resolves inside Render) and run:

```bash
cd backend && npm install
```

```bash
DATABASE_URL="<external connection string>" DB_SSL=true npm run db:seed
```

The same pattern runs any of the `db:*` scripts against the live database —
`db:status` is a good read-only one to start with:

```bash
DATABASE_URL="<external connection string>" DB_SSL=true npm run db:status
```

## 3. URLs

| Path | Serves |
| ---- | ------ |
| `/` | the landing page |
| `/admin` | the admin dashboard (`pages/admin.html`, via a rewrite in `render.yaml`) |
| `/pages/*.html` | every other page, by its own filename |

`/admin` is a rewrite, so the address bar keeps showing `/admin` and the
page's `../`-relative asset links still resolve against the site root.

Two Render behaviours to know before editing these routes:

- **Never point `/admin/` at `/admin` with a redirect.** Render normalises the
  trailing slash before matching, so that rule also matches `/admin` and
  redirects it to itself — an infinite 301 loop. Both spellings are rewrites
  for this reason.
- **A Blueprint sync only adds routes, never removes them.** Deleting a rule
  from `render.yaml` does not delete it from the service; you must also edit it
  out under the static site's *Redirects/Rewrites* tab.

## 4. Verify

```bash
curl https://uitogether-api.onrender.com/api/health
```

Expect `{"success":true,...}` with `"database":"up"`. Then open the static site
URL, register an account, and check the browser console for CORS errors.

## Environment variables reference

Set on **`uitogether-api`** (all but the last already in `render.yaml`):

| Variable        | Set by     | Notes                                             |
| --------------- | ---------- | ------------------------------------------------- |
| `DATABASE_URL`  | blueprint  | Internal connection string from `uitogether-db`    |
| `DB_SSL`        | blueprint  | `false` — the internal network is already private  |
| `DB_SSL_CA`     | optional   | PEM bundle, only to verify a provider's own CA     |
| `JWT_SECRET`    | Render     | Auto-generated; rotating it logs everyone out      |
| `CLIENT_URL`    | blueprint  | The static site's full origin, for CORS            |
| `PORT`          | Render     | Injected; do not override                          |

Set on **`uitogether-web`**:

| Variable       | Notes                                                  |
| -------------- | ------------------------------------------------------ |
| `API_BASE_URL` | Backend origin **including `/api`**, no trailing slash  |

The individual `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME`
variables still work and take precedence over `DATABASE_URL`, so you can
override one field without rewriting the URI. Leave them unset in production.

## Things to know about the free tier

- **The API sleeps after 15 minutes idle.** The first request afterwards takes
  ~30–50 seconds while the instance wakes. This is normal, not a bug.
- **Free PostgreSQL expires after 30 days.** Render deletes it, and there is no
  automatic backup on this plan. Back up anything you care about:
  `pg_dump "<external connection string>" > backup.sql`.
- **Uploaded files do not survive a deploy.** `multer` writes to
  `backend/public/uploads/`, and Render's free filesystem is ephemeral — images
  attached to competitions or lost-and-found posts vanish on the next deploy or
  wake-up. For anything permanent, attach a Render **Disk** (paid) mounted at
  `backend/public/uploads`, or move uploads to Cloudinary or S3.

## Local development is unchanged

`frontend/config.js` keeps the `__API_BASE_URL__` placeholder in the
repository, so `api.js` falls back to `http://localhost:5050/api`. Only the
Render build rewrites it. Leaving `DATABASE_URL` unset keeps the backend
pointed at your local PostgreSQL via the `DB_*` variables in `backend/.env`.

You now need a local **PostgreSQL 13+** rather than MySQL/MAMP:

```bash
createdb uitogether_db && cd backend && npm run db:setup && npm run db:seed
```

## What the port changed

For anyone comparing against the original MySQL version:

- **Driver.** `mysql2` → `pg`. `config/database.js` keeps the same
  `query` / `queryOne` / `withTransaction` surface, and rewrites the
  repositories' `?` placeholders into `$1, $2, …` so the repository layer
  barely changed. It also re-attaches `insertId` and `affectedRows` to results,
  which is why the `create()` functions now end in `RETURNING <primary key>`.
- **Schema.** `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY`; `ENUM`
  columns → `VARCHAR` + `CHECK`; `ON UPDATE CURRENT_TIMESTAMP` → a shared
  `set_updated_at()` trigger; `KEY` → `CREATE INDEX`; `REGEXP` → `~`.
- **Triggers.** `SIGNAL SQLSTATE '45000'` → `RAISE EXCEPTION`, moved into named
  PL/pgSQL functions. The rules they enforce are unchanged.
- **Errors.** `error.middleware.js` now maps PostgreSQL SQLSTATEs (`23505`,
  `23503`, `23514`, `P0001`, …) instead of MySQL `ER_*` names, and reads the
  violated constraint from `error.constraint` rather than parsing it out of the
  message text.
- **Seed data.** `INSERT IGNORE` → `ON CONFLICT DO NOTHING`, plus a block that
  fast-forwards the identity sequences past the hand-written ids — PostgreSQL
  does not advance them for explicit inserts, and without it the first real
  signup would collide with seeded row 1.
